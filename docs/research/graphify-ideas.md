# Borrow Graphify's map, skip its hype

> **Note, 17 October 2026:** after this research the owner decided not to integrate Graphify, only to borrow its ideas. The tasks that came out of it are in [../roadmap.md](../roadmap.md); read this for background and evidence only.

Graphify is an open-source "codebase knowledge graph" skill for coding agents. It parses code locally with tree-sitter (no LLM involved), uses an LLM only for docs, PDFs and images, tags every edge with its provenance, clusters the graph into communities, and serves the result through a slash command, PreToolUse hooks that steer agents away from grep, and an optional 10-tool local MCP server ([GitHub](https://github.com/Graphify-Labs/graphify)). The YouTube Short you asked about, "This Free Tool Cuts Claude Code Token Usage by 49x on Large Codebases", is one of many Shorts promoting it ([YouTube oEmbed](https://www.youtube.com/oembed?url=https://youtube.com/shorts/ELsXhePjBxI&format=json)). I could not read the Short's description or transcript, so I can't say which feature or number it demonstrates beyond its title. The 49x and 71.5x figures trace back to a single first-party run on a mixed corpus of repos, papers and images, measured against "read everything". The one independent test on a real codebase found **about 7.3x**, with **about 240k tokens to build** the graph ([Exchangepedia](https://exchangepedia.com/articles/graphify-honest-benchmark-real-codebase.html)). For CrewChat the main value is not in installing Graphify. The value is in its ideas, and those ideas match a gap your code already has. Today `areas` is the only link between a task and the code it touches, and it is a hand-typed path prefix that nothing derives or checks. A local, deterministic code graph could fill in those areas, widen conflict checks from "same folder" to "same blast radius", and drive short interface-change notices. That last idea has the strongest evidence of anything in this report. All of it can be built without breaking the stdlib-only core, the 127.0.0.1 binding, or the no-telemetry rule. The recommended order: start this week with a zero-code skill pilot, then add an optional `crewchat_graph.py` module that reads a graph file. Leave Graphify's LLM pass, its cloud product, and any syncing of graphs between machines alone.

## Graphify is a tree-sitter graph with an agent-steering layer

Graphify started as a weekend project by Safi Shamsi in April 2026. It is now maintained by Graphify Labs (YC S26), has about 127k GitHub stars, and ships on PyPI as `graphifyy` (two y's) under Apache-2.0 ([GitHub](https://github.com/Graphify-Labs/graphify), [YC](https://www.ycombinator.com/companies/graphify-labs), [Tech Funding News](https://techfundingnews.com/he-built-an-open-source-tool-ai-coding-assistants-couldnt-ignore/)). New versions come out almost every day. On 2026-10-17 the wheel was at 0.9.92, one version past the PyPI page fetched that week ([PyPI](https://pypi.org/project/graphifyy/)). The pipeline runs detect → extract → build → cluster → analyze → report → export. **Code is parsed locally with tree-sitter across about 40 languages, and "nothing leaves the machine"**. Docs, PDFs and images go through a semantic pass run by the host agent's subagents or a configured API key ([GitHub](https://github.com/Graphify-Labs/graphify)). Inspecting the published wheel confirms the schema: every edge carries `source, target, relation, confidence, source_file`, and confidence must be `EXTRACTED`, `INFERRED` or `AMBIGUOUS`. A second pass turns file-level imports into symbol-level `INFERRED` edges. Communities come from Leiden clustering, and an analysis step picks out "god nodes", "surprising connections" and suggested questions for `GRAPH_REPORT.md` ([GitHub](https://github.com/Graphify-Labs/graphify)).

Agents use the graph through three surfaces. `graphify install` writes a `/graphify` skill into more than 20 assistants. On Claude Code it also installs **PreToolUse hooks on `Bash|Grep` and `Read|Glob`** that nudge the agent toward graph queries. The `graphifyy[mcp]` extra runs a local MCP server whose tools include `query_graph` (BFS/DFS, depth 1–6, **`token_budget` default 2000**), `get_neighbors`, `get_community`, `god_nodes` and `shortest_path`. It reloads `graph.json` whenever the file's mtime changes ([docs.graphify.com](https://docs.graphify.com/reference/mcp-tools), [DeepWiki](https://deepwiki.com/safishamsi/graphify/4.2-mcp-server-(serve.py))). The CLI has `query`, `path` and `explain` commands with defined exit codes (0 = answer, 3 = ambiguous, 4 = no match). Queries are logged locally to `~/.cache/graphify-queries.log`, and `GRAPHIFY_QUERY_LOG_DISABLE=1` turns that off ([GitHub](https://github.com/Graphify-Labs/graphify)). Graphify uses no embeddings and no vector store. Retrieval is fuzzy label matching followed by graph traversal: it is cheap and deterministic, but it only finds what your words name.

The tool is open-core. The hosted **Graphify Cloud** serves its MCP endpoint at `api.graphify.com/mcp` with OAuth, and an enterprise Rust engine called Penpax has a waitlist ([docs.graphify.com](https://docs.graphify.com/reference/mcp-tools), [Tech Funding News](https://techfundingnews.com/he-built-an-open-source-tool-ai-coding-assistants-couldnt-ignore/)). That matters for CrewChat. The free local CLI fits your privacy stance, but the cloud product sends your code structure off the machine, so it does not fit.

## Independent tests shrink 49x to roughly 7x, with a real build bill

The token multipliers do not hold up once a real codebase is measured.

| Claim or measurement | Number | Basis |
|---|---|---|
| Original README headline | 71.5x | 52-file mixed corpus (repos, papers, images) vs reading everything ([Exchangepedia](https://exchangepedia.com/articles/graphify-honest-benchmark-real-codebase.html)) |
| Shorts and blogs | 49x, 70x | Re-quotes of the same first-party run ([Stackademic](https://blog.stackademic.com/does-graphify-cut-claude-code-costs-the-token-math-a-skeptic-should-run-first-fdfc989d3bce?gi=dd4d6a4f3691)) |
| Current README | "Cut agent token spend by 80%" | Paid Cloud product, no method given ([PyPI](https://pypi.org/project/graphifyy/)) |
| Independent FastAPI test, about 140 files | **about 7.3x** (6.5–8.1x) | 5 questions; 240k tokens to build, 40k for a 3-file update ([Exchangepedia](https://exchangepedia.com/articles/graphify-honest-benchmark-real-codebase.html)) |
| Graph MCP vs file explorer, 31 repos (a different tool) | **about 10x fewer tokens, answer quality 0.83 vs 0.92** | Same model on both sides ([arXiv 2603.27277](https://arxiv.org/html/2603.27277v1)) |

The independent test also found problems the marketing leaves out. **52% of edges were `INFERRED` with a blanket 0.5 confidence. 96 of 118 communities were single nodes.** grep was often faster for specific lookups, and in a clear-spec implementation session the agent never used the graph at all. Graphify's own token tracker reported a build cost of zero; the real figure came from the subagents' usage ([Exchangepedia](https://exchangepedia.com/articles/graphify-honest-benchmark-real-codebase.html)). Skeptics make a structural point too. A graph speeds up *reading*, not *writing*, because edits still load the raw files. Small repos of around 30 files gain little. A stale graph points agents with confidence at code that has moved ([Stackademic](https://blog.stackademic.com/does-graphify-cut-claude-code-costs-the-token-math-a-skeptic-should-run-first-fdfc989d3bce?gi=dd4d6a4f3691)). Wavect adds that inferred edges are easy to mistake for real ones, that `graph.json` exposes your architecture and file paths, and that daily releases mean retesting on every upgrade. Its advice is a two-week pilot with a pinned version and 20 real questions run against a baseline ([Wavect](https://wavect.io/blog/graphify-review-codebase-knowledge-graph/)). Graphify's own published benchmarks are memory and QA benchmarks with mixed results. It trails supermemory on LOCOMO QA (45.3% vs 49.7%), and its only coding benchmark has **n=6** ([GitHub](https://github.com/Graphify-Labs/graphify)).

The broader literature explains this pattern. The study of a different graph MCP server found that graph agents use far fewer tokens and tool calls but lose on questions that need the full source or an exhaustive search for call sites, and **the authors recommend a hybrid: graph for structure, file reads for source** ([arXiv 2603.27277](https://arxiv.org/html/2603.27277v1)). On a Java codebase, a deterministic AST graph answered 15/15 questions correctly and built in seconds. An LLM-extracted graph answered 13/15, cost **20–45x more**, and **silently skipped 377 of 1,210 files** ([arXiv 2601.08773](https://arxiv.org/html/2601.08773v1)). The honest reading: if you use Graphify on CrewChat, run only its code pass. That pass is free and complete. Expect single-digit savings on orientation questions, and treat graph answers as hints that point an agent to the file it should then read.

## The areas field is where a code graph fits into CrewChat

CrewChat has no code-knowledge layer. Shared context is the owner's rules and skills, the message log and the task sheet. The only link between a task and the code it touches is `areas`, a list of comma-separated path prefixes. `areas_overlap` treats two tasks as overlapping when one prefix contains the other ([crewchat.py:943-947](https://github.com/deepankar17/crewchat/blob/d3c38ea/crewchat.py#L943-L947)), and `_not_yet` refuses a task whose areas overlap a row another agent is holding ([crewchat.py:2440-2457](https://github.com/deepankar17/crewchat/blob/d3c38ea/crewchat.py#L2440-L2457)). Nothing derives or validates `areas`. It comes from free text in `hub_task_add` and the page's task form ([crewchat.py:3375](https://github.com/deepankar17/crewchat/blob/d3c38ea/crewchat.py#L3375)). Beyond that, conflict avoidance is prose: RULES ask agents to message before touching someone's files ([crewchat.py:7708-7710](https://github.com/deepankar17/crewchat/blob/d3c38ea/crewchat.py#L7708-L7710)). So two agents editing `auth/session.py` and `api/login.py` never conflict on the sheet, even when one calls the other. That is exactly the kind of breakage a code graph can catch.

That gap matters more in CrewChat than in single-vendor setups. An analysis of 33,596 agent PRs found textual conflicts in **41.7% of cross-agent PR pairs versus 19.8% of same-agent pairs**, because different agents make different architectural choices and share no claim protocol ([Vaughan](https://codex.danielvaughan.com/2026/07/28/agent-pr-merge-conflicts-concurrent-coding-agents-codex-cli-worktree-isolation-coordination-defence/)). Mixing Claude Code, Cursor and Codex is CrewChat's whole premise. Claude Code's own agent teams offer no file lock or impact analysis, only the advice to "break the work so each teammate owns a different set of files" ([Claude Code docs](https://code.claude.com/docs/en/agent-teams)). The closest prior art, mcp_agent_mail, has TTL file reservations but no code graph ([GitHub](https://github.com/dicklesworthstone/mcp_agent_mail)). The research found no published system that combines a code-structure graph with live claims and warnings across machines, though the search was limited.

CrewChat's design shapes any integration in four ways, and all four point the same direction:

1. **The core stays stdlib-only and single-file.** CONTRIBUTING rejects core dependencies, and optional features follow the `crewchat_cloud` pattern of a separate module imported lazily ([CONTRIBUTING.md](https://github.com/deepankar17/crewchat/blob/d3c38ea/CONTRIBUTING.md), [crewchat.py:5561-5567](https://github.com/deepankar17/crewchat/blob/d3c38ea/crewchat.py#L5561-L5567)). Because `graph.json` is plain JSON, the stdlib `json` module can read it without importing Graphify.
2. **The server binds only to 127.0.0.1.** `BIND = "127.0.0.1"  # Never anything else` ([crewchat.py:59](https://github.com/deepankar17/crewchat/blob/d3c38ea/crewchat.py#L59)), so any graph server you run alongside it should also be local.
3. **CrewChat "collects nothing", and activity reporting deliberately exposes only basenames and program names** ([docs/privacy.md](https://github.com/deepankar17/crewchat/blob/d3c38ea/docs/privacy.md), [crewchat.py:6600-6645](https://github.com/deepankar17/crewchat/blob/d3c38ea/crewchat.py#L6600-L6645)). Graphify's semantic pass and Graphify Cloud would break that unless the owner opts in explicitly.
4. **Only `EXTRA_FIELDS` survive sync between machines, and cloud sync carries no files** ([crewchat.py:110](https://github.com/deepankar17/crewchat/blob/d3c38ea/crewchat.py#L110)). Each machine should build its own graph from its own checkout. Only derived data such as `areas` should travel, and `areas` already syncs for free.

## Five Graphify-era ideas have evidence behind them

Some of the patterns in and around Graphify have measured results for multi-agent coding, not just token claims.

**Interface-change notices have the strongest evidence.** On the STALE benchmark, parallel patches that each pass their tests broke after merging in 97% of constructed Django runs. A roughly **130-token message describing the changed interfaces cut mean interference by 98%** in the synthetic tier and recovered 82% of the constructed tier. Two limits apply: the message was a perfect oracle, and return-type changes still leaked ([arXiv 2609.25396](https://arxiv.org/html/2609.25396)). CrewChat already delivers messages to agents on every turn through its Stop hook, and `hub_send` already describes itself as the way to "warn about a file you are about to change" ([crewchat.py:3205](https://github.com/deepankar17/crewchat/blob/d3c38ea/crewchat.py#L3205)). A graph turns that convention into a targeted, automatic notice sent to the agents whose tasks cover callers of the changed code.

**Splitting work by code cohesion is the next strongest.** Co-Coder builds a file dependency graph, sets hub files aside first, and gives each agent one Infomap cluster. That raised DevEval pass rate from **56.8% to 68.1%**, with a 1.81x speedup and 28% lower cost. Naive file-based parallelism raised cost for little gain ([arXiv 2606.00953](https://arxiv.org/html/2606.00953)). This is what Graphify's Leiden communities and god nodes are good for. Your lead role prompt already says "Keep two agents from editing the same files at the same time" ([crewchat.py:114-176](https://github.com/deepankar17/crewchat/blob/d3c38ea/crewchat.py#L114-L176)). Graph communities would let the lead do that by structure, not by guesswork.

Three smaller ideas are worth copying directly. Graphify's **`token_budget` cap on every graph answer** keeps tool results small, which matters because every CrewChat agent pays for its own context. Its **`EXTRACTED`/`INFERRED`/`AMBIGUOUS` provenance tags** let an agent tell a parsed import from a guess. CrewChat should carry them through to any graph-derived warning so a blanket 0.5 edge never silently blocks a task. And **content-hash caching with mtime hot-reload** keeps rebuilds cheap: incremental re-indexes take about 1.2 s in a comparable system ([arXiv 2603.27277](https://arxiv.org/html/2603.27277v1)). In a multi-agent setting, staleness is the bigger risk, because agent B queries a graph that agent A is changing. Graph answers should therefore carry the commit or file hash they were built from.

One idea needs no code graph at all: a **collaboration graph built from CrewChat's own events**. Each task, claim, message and verdict already exists as a message, so edges like task → touches → file, agent → claimed → task, and answer → approves → task can be stored append-only with timestamps. No LLM extraction is needed. A git-based append-only event log of this kind cut duplicate work between agents from 78% to 0% in one study ([arXiv 2606.19616](https://arxiv.org/abs/2606.19616v1)). CrewChat's `messages.jsonl` is already most of that substrate.

## Conclusion

CrewChat does not need Graphify's headline feature. Shaving 7–10x off orientation reads mostly helps a single agent, it costs real tokens when the LLM pass runs, and the CLI changes daily. What CrewChat needs is the part Graphify treats as plumbing: a cheap, deterministic, provenance-tagged answer to "what else does this change touch?" CrewChat is unusual because it already has the other half. It has claims, cross-machine messaging and a hook that reaches every agent's next turn, and that is exactly where the best evidence (interface notices at −98% interference, cohesion splits at +11 points of pass rate) says a code graph pays off. No published tool seems to join those halves yet.

The main open risk is calibration. A graph that warns too often teaches agents to ignore it, and a stale or inferred edge that blocks a task does real harm. Ship the graph features as warnings first, record how often agents act on them, and treat Graphify's own numbers, including the Short's 49x, as marketing until your own 20-question pilot says otherwise.
